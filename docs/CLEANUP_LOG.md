## fix/freeze-resolved-hunch-verdict

**Scope:** Surfaced while scoping PROGRESS.md's S14 (delete logs older than a chosen date) — its open cascade-behavior question ("does deleting old Events also need to handle Hunches/Verdicts?") led to reading `HunchTabState.kt`'s `toHistoryEntry`, which reconstructs a resolved Hunch's historical verdict by recomputing `computeVerdict()` against whatever Events currently exist, filtered to `occurredAt <= resolvedAt`. Its own comment claimed this keeps history "frozen" — true against *new* Events arriving later, but not against edits or deletions of *old* Events inside that window, which silently changed or dropped a closed Hunch's verdict. That gap already existed for any edit to an old Event; S14's bulk date-range delete would have exposed it constantly. Discussed with the user: resolved Hunches should stay exactly as they were at the moment they closed — fixed by persisting the verdict at resolution time instead of recomputing it live. S14 itself stays a separate, not-yet-started item; this branch is only the prerequisite fix.

**Changes:**

- `HunchEntity` gained nullable `resolved*` columns mirroring `VerdictResult` (tier, eventCount, activeDayCount, windowDays, observedRate, expectedRate, comparisonBand) plus `resolvedVerdictSnapshotTaken: Boolean` — the latter needed because a null `comparisonBand` is also the legitimate result for a Hunch resolved before it ever reached a verdict, so it's the only way to tell "genuinely no verdict" apart from "not yet snapshotted." `HodithDatabase` bumped to v10 via a pure-additive auto-migration (same shape as the existing v7→v8).
- `CaseDetailViewModel.resolveHunch` now fetches the Case/Events directly from the repository (not `uiState.value`, which only reflects live data while something is actively collecting it) and persists the computed verdict snapshot alongside `resolvedAt`.
- `HunchTabState.toHistoryEntry` reads the persisted snapshot when present, falling back to the old live-recompute path only as a defensive measure for a row not yet backfilled.
- A schema migration can't run `computeVerdict` (Kotlin domain logic), so it can't backfill pre-existing resolved Hunches — `HodithRepository.backfillResolvedHunchVerdicts()` does that as a one-time-per-row sweep, called from `HodithApplication.onCreate` on every launch (a no-op once every row is snapshotted), freezing each pre-existing resolved Hunch using whatever Events survive at upgrade time.
- `domain/Verdict.kt` gained two small extension functions, `HunchEntity.withResolvedVerdictSnapshot(result)` and `HunchEntity.resolvedVerdictSnapshotOrNull()`, found during the checklist walk below.

## feat/log-tab-paged-query

**Scope:** PROGRESS.md's F4 — the Log tab's `CaseDetailViewModel.uiState` read a Case's entire event history (`EventDao.observeEventsWithTagsForCase`) and re-sorted it all in memory (`sortEventsForLog`) into one `LazyColumn` on every recomposition. The request was specifically to show the 30 most recent events with a "Show more" button (+50 per tap), and to have that genuinely resolve F4 rather than only capping what's rendered — so the fix is a real capped/sorted SQL query, not a client-side window over the full list.

**Changes:**

- **Two new `EventDao` queries** (`observeEventsWithTagsForCasePagedByStart`/`...PagedByEnd`), each `LIMIT`-capped and ordered in SQL rather than in Kotlin. `PagedByEnd` is the one genuinely new bit of SQL in this DAO — a conditional `CASE WHEN ... END DESC` term floating a running `START_STOP` event first. Two single-purpose queries rather than one dynamic-`ORDER BY` query keyed on sort order, matching this DAO's existing small/single-purpose style.
- **New `data/LogSortOrder.kt`** (moved out of `viewmodel/LogSort.kt`) and **new `data/LogEventsPage.kt`** (`events` + `hasMore`). `LogSortOrder` had to move because `RoomHodithRepository` now branches on it to pick a DAO method, and `data` can't depend on `viewmodel`.
- **`HodithRepository.observeLogEventsForCase(caseId, order, limit, durationMode)`** — additive; `observeEventsWithTagsForCase` is untouched and still serves `ShareViewModel`/`CaseEditViewModel`/`LogDetailScreenViewModel`, plus `CaseDetailViewModel`'s own ongoing-event detection, Insights/Hunch stats, and the Log tab's summary line (`eventCount`/`observedDays`, which needs the *earliest* event — a capped query could never supply that). `RoomHodithRepository` fetches `limit + 1` and trims to compute `hasMore`, no separate `COUNT(*)` subscription. `FakeHodithRepository` mirrors the same sort/trim logic in Kotlin.
