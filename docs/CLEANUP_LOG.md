# HODITH — Cleanup Log

A record of the 5 most recent cleanup passes, newest first (ordering, not dating, marks recency — see CLAUDE.md's no-dates rule). After any significant feature work, actually walk through every applicable item in [CLEANUP_CHECKLIST.md](CLEANUP_CHECKLIST.md) against the real diff first — an entry here records what that walk-through found, it isn't a template to fill in from memory of what changed. Then add a new entry above the previous one: what was found and fixed, what was deferred with a reason, and which sections didn't apply and why.

**Retention:** only the 5 newest entries are kept here. When adding one pushes the count past 5, delete the oldest entry in the same commit — its content still lives in git history and is reachable via `git log -- docs/CLEANUP_LOG.md`.

## feature/trend-cadence-recency

**Scope:** User-reported bug: a tag's "rising" trend (and several sibling Trends findings) could keep reading as current long after the underlying burst had aged out, because every count/window-based detector answered "was the second half/window different from the first" rather than "is that difference still true right now." Added a shared cadence/recency helper (`domain/Cadence.kt` — median-based typical interval, a derived recency threshold) and wired it into `FREQUENCY_SHIFT` (magnitude floor + cadence-sized window replacing the fixed 30 days + recency gate), `TAG_SHARE_SHIFT` (per-tag cadence-cut recent/prior split, suppressing a tag whose own cadence can't be assessed rather than falling back to a stale split), `GAP_SHIFT` (cadence-resized split + a live-gap contradiction gate), `STREAK_SHIFT` (recency gate only), and `TREND_SLOPE` (recency gate + a reversal-consistency check against the most recent cadence-relative segment). Reworded `RECURRENCE_SHAPE`'s Voice copy (×3) from present-tense ("Often comes back quickly") to present-perfect, since that finding is a lifetime distribution-shape fact with no recency weighting at all and the old phrasing implied currency it never had. `WENT_QUIET` and `CHANGE_POINT` were confirmed already correct/out of scope and left untouched (change point's own "single split only" limitation spun out to PROGRESS.md as a separate, smaller item).

**Walked:** CLEANUP_CHECKLIST.md section by section against the diff (2 new files — `Cadence.kt`/`CadenceTest.kt` — plus changes across `StatsEngine(Test)`, `InsightsEngine(Test)`, `Trends(Engine)(Test)`, `Stats.kt`, `HeroRate(Test)`, `Voice.kt`, `InsightsTab.kt`, `InsightsTabStateTest`, `ShareCardStateTest`, `ShareCardTemplateTest`, `DemoDataSeederTest`, and 3 docs). `ktlintCheck`, `lintDebug`, `test` (full unit suite, 1249 tests), and `assembleDebug` all pass; `compileDebugAndroidTestKotlin` verified separately. No instrumented run against a device this pass — every changed function is pure Kotlin domain logic plus one UI call-site read (`finding.windowDays ?: TREND_WINDOW_DAYS`), already covered by the JVM suite and a `ShareCardTemplateTest` fixture update.

**Found & fixed:**
- `computeHeroRate`/`caseHeroRate` (`HeroRate.kt`) silently assumed the trend window was always the fixed `TREND_WINDOW_DAYS` (both the headline rate's own denominator and the comparison's prior-rate conversion) — not caught by the original plan review, found while tracing every caller of `computeTrendStats`. Fixed to read `TrendStats.windowDays` instead; a dedicated `HeroRateTest` case pins it (`uses the trend's own window, not a hardcoded 30 days`).
- `TrendFinding`/`TrendStats` gained a `windowDays` field; the `Voice` interface's `insightsFrequencyShiftEvidenceLabel()` changed from a hardcoded "30 days" string to taking the real window per voice. The UI call site reads `finding.windowDays ?: TREND_WINDOW_DAYS` rather than `checkNotNull` — preview/test fixtures that predate this field (`TrendsListScreen.kt`'s preview, `CaseDetailInsightsTabTest.kt`) don't need updating, confirmed by inspection rather than assumption.
- Four `DemoDataSeederTest` cases (Coffee, Tantrum, Lost my keys, Noisy neighbours) asserted exact Trends finding sets built against the old no-floor/fixed-window behavior. Each discrepancy traced to its actual cause via targeted debug prints before updating the assertion, not guessed: Tantrum's and Lost my keys' old `FREQUENCY_SHIFT` finding was a bare 1-count difference (exactly the bug being fixed) — now correctly absent; Coffee's recent surge and Noisy neighbours' BURSTY clustering legitimately expose a real `GAP_SHIFT`/`FREQUENCY_SHIFT` the old fixed-window comparison missed — now correctly present.
- `InsightsTabStateTest`'s two `TREND_SLOPE`-outcome-gating fixtures used `now` 5 days past their last event, incidentally exceeding the new recency threshold for daily-cadence data and suppressing the finding the tests were actually about; its hero-rate comparison test and `ShareCardStateTest`'s two trends-visibility tests relied on perfectly uniform event spacing that can never clear the new magnitude floor (sampling noise, not a real signal) — rebuilt each with a deliberate, verified shift instead of adjusting assertions to match noise.
- `TrendsEngineTest`'s shared `gapStatsOf` fixture helper defaulted `currentGapDays` to `0`, which the new live-gap contradiction gate reads as "the gap just closed" — contradicting nearly every UP-shift fixture built from it. Changed the default to the gap list's own last entry (a neutral assumption) rather than hand-fixing dozens of call sites individually.

**Deferred:**
- `TAG_OUTCOME`/`WEEKDAY_WEEKEND_SPLIT` Voice copy's own milder present-tense phrasing ("$tag lasts longer", "Leans toward weekends") — flagged during design as the same pattern `RECURRENCE_SHAPE` had, but explicitly scoped as optional and lower priority; not touched this pass.
- `computeChangePoint`'s single-best-split limitation (can't detect a reversal back) — spun out to PROGRESS.md as its own item; genuinely separate from this pass's staleness fix.

**Considered and declined:**
- Falling back to the old count-based half-split for a `TAG_SHARE_SHIFT` tag whose own cadence can't be assessed — would silently reintroduce the exact staleness risk being fixed for exactly the sparsest tags. Suppressing the tag entirely (no finding) was chosen instead, reversing the original design sketch after review.
- Mean instead of median for the shared cadence helper's "typical interval" — median is a deliberate, scoped divergence from this codebase's existing mean-based `GapStats.averageGapDays`, specifically because it's robust to the burst-then-quiet shape this whole fix targets; a plain mean would be pulled by exactly the outlier this fix needs to see past.

**Checks:**
- Duplication: no new Trends detector added; the new cadence logic reuses the existing `shiftDirectionFor`/`daysBetween` primitives rather than duplicating threshold logic, and is itself centralized in one new file (`Cadence.kt`) rather than re-derived per detector.
- Decoupling: `Cadence.kt` takes `now`/`zone` as parameters throughout, no direct `Clock`/`System.currentTimeMillis()` reads; no `android.*` imports; no `java.time` usage (checked via `git grep -n "^import java\.time" -- app/src/main/kotlin`, zero hits).
- Hardcoded values: every new threshold is a named constant in the domain layer (`CADENCE_RECENCY_FLOOR_DAYS`, `CADENCE_RECENCY_MULTIPLIER`, `FREQUENCY_SHIFT_MIN_ABSOLUTE_COUNT_DELTA`, etc.), each reviewed and signed off with the user by exact value rather than left as an implementation guess.
- Naming: the one new/changed Voice key (`insightsFrequencyShiftEvidenceLabel`'s signature, `RECURRENCE_SHAPE`'s strings) updated in all three voices in the same commit.
- Spec review: `HODITH_SPEC.md` §10 updated — Gap/Streak/Frequency/Tag-share-shift bullets, Change point's own cross-reference, Trend slope's gating description, and the Summary hero's rate-window line all reworded off the fixed-30-day assumption.
- Tests: bug fixed → regression test added at every layer (new `CadenceTest.kt` unit tests on the helper itself; per-detector boundary/gate tests in `StatsEngineTest`/`InsightsEngineTest`; a paired burst-vs-active integration test in `TrendsEngineTest` against `computeTrendFindings` itself, proving the gate isn't vacuously always-suppressing). Existing tests reviewed individually for *why* they broke (see Found & fixed) before any assertion was changed, not just re-run until green.

**Docs updated:** HODITH_SPEC.md (§10, five bullets + the Summary hero line); TESTING.md (Stats & visual data prep row — hero rate's window wording, the new `CadenceTest` coverage, gap/streak/frequency/tag-share-shift's new gates, trend slope's recency/reversal checks); PROGRESS.md (new standalone item for change point's reversal gap); this entry (oldest entry, `fix/single-case-widget-missing-case-edit-icon`, removed per the 5-entry retention rule).

## fix/single-case-widget-missing-case-edit-icon — remove hidden content, add render-test guard

**Scope:** Continuation of the same open PR: reviewing the previous pass's "✎" edit icon on a real emulator surfaced two rendering bugs the existing instrumented suite doesn't catch — an archived/deleted Case's "Case is gone" message clips down to a single word, and some Case icons clip at the bottom. Traced the root cause to `WidgetRenderTestFixtures.kt`'s `renderedView()`, which only calls `AppWidgetHost.createView()` — no `measure()`/`layout()`, no `AppWidgetHostView` size options, never attached to a window — so every `WidgetActionsFlowTest` assertion walks an unmeasured View tree that proves nothing about the widget's real, non-resizable declared size (`single_case_widget_info.xml`: `minWidth="60dp" minHeight="60dp"`, no `resizeMode`). Rather than patch the symptom, redesigned the Single-case widget to stop rendering content that can't reliably fit: bound-Case state now shows only the icon (its own non-weighted zone, sized to its own content, so a sibling can never starve it of height) and a log button filling the rest of the tile — no subtitle, "Ongoing" pill, elapsed time, or count; missing-Case state shows "Edit" + "✎" filling the same shape, both reopening the configure Activity, with the old message and its separate `MainActivity` tap removed outright.
